# Retries & Recovery

Von handles delivery failures automatically with retries, circuit breakers, and replay.

<PageActions />

## Automatic retries

When a delivery fails (non-2xx response or timeout), Von retries it with exponential backoff starting at 1 second and doubling each attempt:

| Attempt | Delay |
| --- | --- |
| 1 | Immediate |
| 2 | ~1 second |
| 3 | ~2 seconds |
| 4 | ~4 seconds |

Each endpoint can configure its own `maxAttempts` (1 to 10, default 4) and `timeoutMs` (1 to 60 seconds, default 30 seconds).

```typescript
const { data: endpoint } = await von.endpoints.create({
  url: "https://your-app.com/webhooks",
  maxAttempts: 8,
  timeoutMs: 15000,
});
```

<Note>
  `maxAttempts` is the total number of attempts including the first try, not the number of retries after failure.
</Note>

A delivery is marked `failed` only after all attempts are exhausted.

## Circuit breakers

Von protects unstable endpoints with a circuit breaker, stopping delivery temporarily when an endpoint fails repeatedly to let it recover.

| State | Behavior |
| --- | --- |
| `closed` | Normal state where deliveries flow and consecutive failures are counted. |
| `open` | Activates after 5 consecutive failures and immediately skips deliveries as `circuit_open`. |
| `half_open` | Activates after 5 minutes in `open`, lets deliveries through to test recovery, then closes on success or reopens for another 5 minutes on failure. |

| Parameter | Value |
| --- | --- |
| Failure threshold | 5 consecutive failures |
| Reset timeout | 5 minutes |

Only consecutive failures count toward the threshold, and any successful delivery resets the failure counter to zero. When the circuit closes after a successful delivery, Von emails the organization owner to confirm deliveries have resumed.

If an endpoint stays in a failure state for 5 consecutive days, Von disables it and sends a notification. Re-enable the endpoint and replay skipped deliveries once the issue is resolved.

<Tip title="Replaying circuit-skipped deliveries">
  Deliveries skipped while the circuit is open are marked `circuit_open`, and after the endpoint recovers you can bulk replay them.
</Tip>

## Replaying failed deliveries

### Single event

Re-deliver one event to all its endpoints, or target specific ones:

```text
POST /webhooks/events/evt_xxx/replay
{ "endpointIds": ["ep_abc"] }
```

### Bulk replay

Re-deliver all failed deliveries since a given date:

```text
POST /webhooks/events/replay
{ "since": "2025-01-15T00:00:00Z", "status": "failed" }
```

You can filter by `status` and `endpointId` to narrow the scope.

## Debugging retries

Use delivery attempt history when you need the full timeline for one delivery:

```text
GET /webhooks/deliveries/dlv_xxx/attempts?sort=asc
```

Use analytics when you need trend-level retry metrics across the organization:

| Route | Use |
| --- | --- |
| [Analytics](/analytics) | Entry point and query patterns |
| `GET /analytics/retries` | Retry totals, rates, and attempt distribution |
| `GET /analytics/timeseries` | Time-bucketed trend metrics |

## Endpoint statuses

Von sends deliveries only to endpoints in `active` status, and switching to `paused` or `disabled` affects future deliveries but not jobs already queued.

| Status | Behavior |
| --- | --- |
| `active` | Deliveries are sent normally |
| `paused` | Deliveries in flight are marked `paused`, not attempted |
| `disabled` | Deliveries in flight are marked `skipped`, not attempted. Von can also set this automatically after 5 days of sustained delivery failures. |

Pausing is useful during maintenance windows, since deliveries marked `paused` can be replayed once the endpoint is active again.

## Worker configuration

When self-hosting, you can configure the delivery worker:

| Variable | Default | Description |
| --- | --- | --- |
| `WORKER_CONCURRENCY` | 50 | Concurrent delivery jobs (max 500) |
| `EVENT_RETENTION_DAYS` | 90 | Days before events are cleaned up |
| `DELIVERY_RETENTION_DAYS` | 90 | Days before deliveries and delivery attempt history are cleaned up |
