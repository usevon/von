# API Keys & Environments

Manage access to the Von API with environment-scoped keys and granular permission scopes.

<PageActions />

## Key format

API keys are prefixed by environment:

| Environment | Prefix |
| --- | --- |
| Development | `von_dev_` |
| Staging | `von_stg_` |
| Production | `von_prod_` |

Keys are 64 random characters plus an HMAC signature suffix, making them safe to identify by prefix in logs without exposing the full key.

## Creating a key

Create keys from the [dashboard](https://app.usevon.com/settings/api-keys) or the API. The full key is shown once at creation, so copy it immediately. Keys are scoped to a user and carry the organization context for every request they make.

<Properties>
  <Property name="name" type="string" required>
    A display label, max 64 characters.
  </Property>
  <Property name="environment" type="string" required>
    The environment this key belongs to: `dev`, `staging`, or `prod`.
  </Property>
  <Property name="scopes" type="string[]">
    Defaults to `["*"]` for full access.
  </Property>
  <Property name="expiresIn" type="number">
    Seconds until expiry, max 365 days. Omit for no expiration.
  </Property>
  <Property name="organizationId" type="string">
    Defaults to your active organization.
  </Property>
</Properties>

## Scopes

Each key is scoped to exactly what it needs:

| Scope | Access |
| --- | --- |
| `*` | Full access to everything |
| `read:*` | Read access to all resources |
| `write:*` | Write access to all resources |
| `read:webhooks` | List and view events and deliveries |
| `write:webhooks` | Send events, replay deliveries |
| `read:endpoints` | List and view endpoints |
| `write:endpoints` | Create, update, delete endpoints |
| `read:inbound` | List and view inbound endpoints |
| `write:inbound` | Create, update, delete inbound endpoints |
| `read:versions` | List and view versions |
| `write:versions` | Create, update, delete versions |
| `read:analytics` | Read analytics resources |
| `read:tunnels` | List active tunnels |
| `write:tunnels` | Register and rotate tunnels |

Scopes are hierarchical: `*` grants everything, `read:*` grants all read scopes, `write:*` grants all write scopes.

Use `read:analytics`, `read:*`, or `*` to access analytics routes with API keys.

<Tip title="Avoid using * in production keys">
  Full-access keys are useful in development, but in production use `read:*` or resource-specific scopes to reduce impact if a key leaks.
</Tip>

## Using a key

Pass the key as a Bearer token in the `Authorization` header:

```bash
curl -H "Authorization: Bearer von_prod_xxx" \
  https://api.usevon.com/endpoints
```

Or configure the SDK:

```typescript
const von = new Von({
  apiKey: "von_prod_xxx",
});
```

The SDK also reads from the `VON_API_KEY` environment variable automatically.

## Key lifecycle

| Lifecycle step | Behavior |
| --- | --- |
| Listing | Full key values are never returned after creation; use the `start` prefix (first 12 chars) for identification. |
| Disabling | Set `disabled` to stop key usage immediately without deleting metadata. |
| Expiration | Set `expiresIn` at creation (max 365 days); expired keys are deleted automatically on next use. |
| Rotation | Create a replacement key, deploy it, verify traffic, then disable and delete the old key. |

There is no atomic rotation endpoint, so keep a short overlap window during rotation.

## Security details

| Topic | Behavior |
| --- | --- |
| Storage | Keys are hashed with SHA-256; only the `start` prefix is stored in plaintext for identification. |
| Integrity verification | Production keys include an HMAC suffix, and invalid signatures are rejected before database lookup. |
| Rate limiting | Authenticated routes are IP rate-limited, and throughput limits apply to webhook sends/replays and endpoint writes. |
| Usage tracking | `lastUsedAt` updates are buffered in Redis and flushed to the database every 5 minutes. |

## Scopes in practice

Assign the narrowest scope set that covers what the key needs.

| Use case | Scopes | Notes |
| --- | --- | --- |
| Read-only monitoring | `["read:*"]` | Safe for dashboards and observability tooling |
| Webhook sender service | `["write:webhooks"]` | Cannot read, modify endpoints, or manage keys |
| Endpoint admin | `["read:endpoints", "write:endpoints"]` | No access to events or deliveries |
| CI smoke tests | `["read:webhooks", "read:endpoints"]` | Pair with a short `expiresIn` |

```typescript
const senderKey = await von.apiKeys.create({
  name: "webhook-sender-prod",
  environment: "prod",
  scopes: ["write:webhooks"],
});

const readKey = await von.apiKeys.create({
  name: "observability-pipeline",
  environment: "prod",
  scopes: ["read:*"],
});
```

## Security operations

### Rotating keys without downtime

There is no atomic rotation endpoint. Create a new key with the same scopes, deploy it across services, confirm it appears in `lastUsedAt`, then disable and delete the old one.

<Tip title="Keep the overlap window short">
  Disable the old key first to stop request acceptance, then delete it after confirming no service still depends on it.
</Tip>

### If a key is exposed

1. Disable the key from the dashboard or via `PATCH /api-keys/:id` with `{ "disabled": true }`.
2. Create a replacement and rotate all services to it.
3. Delete the old key.
4. Search logs by the `start` prefix to understand what was accessed before rotating downstream secrets.

### Auditing

The audit log records `apikey.created`, `apikey.updated`, and `apikey.deleted`; view it in Settings or query `GET /audit-log` with a session (API keys are always rejected).
